# 通用 Story / 模块详细设计 Markdown 规范

> 适用场景：基于需求/Story 与代码仓库，输出结构清爽、主次分明的详细设计文稿（可独立交付评审，也可直接作为生成 `.docx` 详细设计说明书的设计输入）。

---

## 强制写作原则

1. **结合代码核对**：文中的所有目录/模块名、类名、接口、方法签名、常量/阈值、枚举、事件名，必须与代码仓库逐一核对（若为先设计后编码，须显式标注待实现假设）。
2. **总分结构，拒绝堆砌**：第 2 章禁止把所有流程塞进一张巨图或大段文字；必须先画一张**全景主干图**，再按关键环节逐节拆解，每节配**局部流程图或时序图**。
3. **重类图与职责，不写实现代码**：第 3 章按职责拆分为多组清晰类图，**禁止贴函数内部实现体、控制流源码或逐行流水账伪代码**；图下只列出核心类与重要函数**“做什么事情（能力边界与协作关系）”**。

---

## 标准章节骨架

```markdown
# Story 设计文档：<主题 / 模块名称>

## 1. 概述

简要说明本 Story / 需求聚焦的核心职责（2~3 条）：
1. **职责一**：...
2. **职责二**：...

整体分层职责：
- **<层名>（`<模块/目录>`）**：<一句话职责>
- ...

---

## 2. 详细设计

> 本章采用“全景主干 + 关键环节拆解”的总分结构，聚焦主流程与关键边界分支，略去非核心枝节。

### 2.1 系统运行主干：<从起点到稳态闭环>

用 1~2 句话说明主干链路，随后给出全景流程图（含核心异常/自愈分支）：

```mermaid
flowchart TD
    %% 主链路节点 + 关键异常分流闭环
```

---

### 2.2 <关键环节 A：如配置解析 / 状态初始化>

简述分段职责（1~3 句）+ 该环节独立流程图或时序图：

```mermaid
flowchart TD
    %% 局部拆解，聚焦边界校验与失败分支
```

---

### 2.3 <关键环节 B：如建连选连 / 业务状态决策>

简述职责 + 决策流程图（如适用） + 跨对象交互/异常容灾时序图：

```mermaid
sequenceDiagram
    autonumber
    %% 正常主交互 + 异常/超时/断链响应时序
```

---

## 3. 代码设计（Class 与 Interface 结构）

按模块/职责划分为多组独立类图，直观呈现核心 `class`、`interface` 与 `event` 的能力边界及协作关系；**不写内部实现细节，仅列出重要对外函数及其职责**。

### 3.1 <职责分组 1（模块名）>

```mermaid
classDiagram
    direction TB
    %% 只放关键属性与重要对外方法签名，不放内部私有细节
```

- **`<ClassA>`**：<核心职责定位 + 重要函数做什么事情（如配置、启停、分批读取、超时保护）>。
- **`<InterfaceB>`**：<回调/扩展契约职责，说明何时被调用、返回什么>。

### 3.2 <职责分组 2（模块名）>
...
```
